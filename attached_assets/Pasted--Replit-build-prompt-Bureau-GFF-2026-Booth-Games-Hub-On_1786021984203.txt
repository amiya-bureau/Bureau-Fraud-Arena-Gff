# Replit build prompt - Bureau GFF 2026 Booth Games Hub

One web app hosting three games, a shared lead-capture form, per-game scores and one cumulative leaderboard.

Paste everything between the two horizontal rules into Replit Agent as your first message. It is long on purpose - Replit Agent builds far better from a complete spec than from a vague one it has to guess at. The two data blocks at the end are content, not suggestions.

---

Build a full-stack web app called **Bureau Fraud Arena** - the game hub for Bureau's booth at Global Fintech Fest 2026 (Booth G8, 9-11 Sep 2026, Jio World Convention Centre Mumbai). It runs on three touchscreen kiosks at the booth and on visitors' own phones via QR code.

Three games, one entry form, one leaderboard. Every play is a consented sales lead, so the form is not optional decoration - it is the reason the booth exists.

## Tech stack

- **Next.js 14+ App Router, TypeScript, Tailwind CSS.**
- **Replit's native SQL Database** for persistence - the Postgres one, created from the Tools dock. It auto-injects `DATABASE_URL`, so read the connection string from that env var and never hardcode credentials.
- **Drizzle ORM** with a migration file, plus a seed script. Replit's built-in Drizzle Studio then gives the ops desk a visual table browser for free, which is genuinely useful mid-event.

### Use the SQL database, not the key-value store

Replit offers two native databases and only one of them works here. Use **Replit SQL Database (Postgres)**. Do **not** use **Replit DB, the key-value store**, and do not let it get substituted in as a convenient default. Three reasons, in order of how badly each one bites:

1. **Concurrency.** Three kiosks and an unknown number of phones write at the same time. The leaderboard needs read-modify-write on shared aggregates, and a KV store gives no transactions, so simultaneous plays silently clobber each other's scores. On a trade-show floor that surfaces as "my score disappeared" in front of a prospect.
2. **No aggregation.** Best-run-per-player-per-day, per-game ranks, the all-three bonus and the CSV export are all queries. In Postgres they are a view. In KV they are a full scan of every key on every leaderboard poll, every ten seconds, on venue WiFi.
3. **Limits.** Replit DB caps at roughly 5,000 keys and 50 MiB. Players plus runs plus any index keys across a two-day event with three games will crowd that ceiling, and hitting it mid-event is unrecoverable.

Also do not use SQLite (a redeploy wipes it), an in-memory store, or `localStorage` for anything that matters. A kiosk browser refresh must not cost anyone their score.

Set the database up and prove `DATABASE_URL` connects **before writing any UI**. If it is missing, stop and tell me rather than falling back to another store.
- `qrcode` npm package for QR generation, rendered server-side to a data URL.
- No auth, no third-party analytics, no payment anything.

## Data model

```
players
  id              uuid pk
  work_name       text not null
  email           text not null            -- lowercased, the identity key
  phone           text not null            -- 10-digit Indian mobile
  company         text not null
  consent_at      timestamptz not null     -- DPDP consent, never null
  created_at      timestamptz default now()
  unique(email)

runs
  id              uuid pk
  player_id       uuid fk -> players.id
  game            text  -- 'spot_the_fraud' | 'spoof_the_system' | 'fraud_detective'
  points          int not null
  detail          jsonb  -- per-game breakdown, see each game section
  source          text  -- 'kiosk' | 'phone'
  event_day       date  -- derived from created_at in Asia/Kolkata
  created_at      timestamptz default now()

-- Leaderboard is a VIEW, not a table. Never store aggregate scores.
```

**The one scoring rule that governs everything:** a player's score for a game is their **best single run** for that game, per day. Not their latest, not their sum. Replays are allowed and encouraged - the leaderboard just ignores the worse ones. Identity is the lowercased email, so a kiosk play and a phone play by the same person merge automatically.

## Shared entry form

Every game starts with the identical form. Fields, all required:

- **Work name** - non-empty, at least 2 characters
- **Work email** - valid format. Reject obvious free-mail domains (gmail, yahoo, outlook, hotmail, rediffmail, proton) with the inline message "Please use your work email" - this is a B2B booth and the lead quality matters more than the play count. Allow an override link reading "I don't have one" that accepts any valid email but flags the row.
- **Phone** - exactly 10 digits, first digit 6-9. Strip spaces, dashes and a leading +91 before validating.
- **Company** - non-empty
- **DPDP consent checkbox** - unticked by default, and the consent text must be visible on screen, not hidden behind a link. Use: "I agree that Bureau may contact me about its products and store the details above. I can withdraw consent any time by writing to privacy@bureau.id." Nothing submits until this is ticked.

If the email already exists, do not error and do not create a duplicate - recognise them, greet them by first name ("Welcome back, Priya"), skip straight to the rules screen, and attach the new run to the existing player.

Every field needs a large touch target and the numeric keypad on phones (`inputMode="numeric"` for phone). Assume wet fingers, bad lighting and someone waiting behind them.

## Rules screen - before every game, every time

Each game shows a rules screen after the form and before play. Non-negotiable, and it must be skimmable in about eight seconds:

- Game name and a one-line premise
- How scoring works, with the maximum stated plainly ("Up to 100 points")
- What ends a run
- Lifelines or attempts available
- A large "Start" button, and a "Show me an example" link that expands one worked example inline

Also show the player's current standing if they have played before: "Your best so far: 62 pts, rank 14."

## QR code on every game

Every game's kiosk screen shows a QR in a persistent corner panel, plus a full-screen QR on the attract loop. Scanning it opens that game directly on the visitor's phone at `/{game}?src=qr`.

A phone play is an **independent run**. The player fills the form on their phone (or is recognised by email if they already played), plays their own game, and their score merges into the same leaderboard under the same email. There is no session handoff between kiosk and phone and no pairing code - keep it stateless and simple. Tag the run `source = 'phone'` so we can report on it afterwards.

Print the caption "Scan to play on your phone - your score counts the same" under every QR. Generate QRs server-side against the deployed Replit URL read from an env var, never a hardcoded localhost.

# GAME 1 - Spot the Fraud

A ten-level ladder of fraud questions that get harder as you climb. Caps at **100 points**.

Read `LEVELS` and `QUESTIONS` from the Spot the Fraud data block. All content is authored and DS-vetted - use it verbatim, do not write your own questions.

## The ladder

Points per level are 4, 5, 6, 7, 8, 10, 12, 14, 16, 18 and total exactly 100. Assert this on boot and log loudly if it ever fails.

- **Levels 1-5** single answer. **Levels 6-10** multi-select, option count rising 6 to 8.
- **Levels 3, 7, 9** are spot-the-fake image questions. The other seven are text questions about fraud - mostly network-level fraud (rings, mule chains, device farms, identity clusters), with Level 1 as an easier consumer-scam on-ramp.
- Per-level timers come from the data (15-40 seconds). Timer expiry ends the run.
- Clearing Level 5 earns the **Achiever** tier, clearing Level 10 earns **Master**, playing at all earns **Participation**.

## Scoring

Single-answer levels: correct scores the level's points and advances; wrong or timeout scores 0 for that level and **ends the run**.

Multi-select levels: an exact set scores full points and advances. Exactly one swap - one wrong option in place of one correct one - scores `nearMiss` (half the level value, rounded down) and ends the run without counting as cleared. Two or more swaps, or a timeout, scores 0 and ends the run.

**Points banked at each level are always kept.** There is no all-or-nothing forfeit. Someone who dies at Level 6 walks away with 40 points and the feeling that Level 7 was reachable, which is exactly what makes them replay.

On multi-select levels the header states how many to pick ("Select 2 of 6") and **Submit stays disabled until exactly that many are selected**. This stops people selecting everything and means the only possible error is a swap.

## Lifelines

**Skip** - available from the start on Levels 1-4 and 6-9, blocked on 5 and 10 because the tier gates must be earned. Advances the player, scores 0 for that level, preserves the run.

**50:50** - starts **locked**. It is unlocked by the Bureau question (below) and then works on Levels 5-10 only. Removes wrong options only, never a correct one, using `fiftyRemoves` from the data. Costs 3 points off that level's award, floored at 1. On image grids it removes real (non-fake) tiles.

Render both buttons at all times with distinct locked / available / used states. A greyed-out 50:50 reading "Unlocks at the Bureau question" is doing real work - it builds anticipation for the brand moment.

## The Bureau question

Between Level 4 and Level 5, once per run, drawn at random from `BUREAU_QUESTIONS`. **The answer is always "Bureau."** This is the sponsor-question mechanic from the Amazon app quizzes.

- Worth **zero points** - it cannot move the score, so the 100 cap holds.
- Answering it **unlocks the 50:50** for Levels 5-10.
- **No timer, no fail state.** A wrong tap shakes the card and re-prompts. Nobody can lose here or get stuck.
- Style it visibly apart from the ladder - Bureau blue background, a "Bonus - unlock your 50:50" banner. It should read as a gift, not an ad.
- **Fallback that matters:** if a run ends before Level 4, show the Bureau question on the game-over screen instead, as a consolation unlock granting a 50:50 for their next run. Every player must see it exactly once per run.

## Image questions

The real photography does not exist yet. Render each image option as a **labelled placeholder**: neutral grey tile, dashed border, image icon, the option text from the data (which describes the photo and its visual tell) in small type, tile number in the corner. Build one `<ImageTile>` component taking an optional `src` prop so swapping in real assets later is one URL per option and no logic change. Comment it `TODO: swap placeholder for real asset`.

Grid sizes: Level 3 shows 2 side by side, Level 7 shows 6 in a 3x2, Level 9 shows 8 in a 4x2.

## Explain screen

After **every** answer, right or wrong, show the question's `why` text and its `hook` - the Bureau capability that catches this in production. Auto-advance after 4 seconds with a visible progress bar, plus a Next button to skip the wait.

This screen is the entire commercial point of the game. It is where the host starts a conversation. Give it real visual weight; do not degrade it to a toast.

# GAME 2 - Spoof the System

The jackpot challenge. Three attempts against progressively stricter detectors. Caps at **75 points**.

## Flow

Entry form, rules, then: the visitor generates a synthetic or AI image on their own phone using any tool they like, uploads it, and watches Bureau's detectors run. Three attempts, each against a stricter detector level. Fool it and climb; fail and the run ends. After each successful fool, offer an explicit **quit-or-continue** choice - banked points are kept either way.

Because the upload happens from a phone, this game's QR is the primary path, not a secondary one. The kiosk should show a large QR and a live status panel; the actual upload UI is the phone view.

## The ladder

| Outcome | Points | Reward |
|---|---|---|
| 1st attempt fails | 15 | Game over - Participation tier |
| 1st fool, 2nd fails | 40 | Achiever tier gift |
| 1st + 2nd fool, 3rd fails | 60 | AirPods finale draw entry |
| All three fooled | 75 | iPad MEGA draw entry + wall of fame |

Everyone scores at least 15 for turning up and trying. Detector level 3 is deliberately tuned so full-ladder qualifiers stay in single digits across the event.

## The detector - read this carefully

**We do not have a real detector API in this build.** So implement the verdict behind exactly one clearly marked async function and nothing else:

```ts
// lib/detector.ts
// TODO: REPLACE WITH BUREAU'S REAL DETECTOR API BEFORE THE EVENT.
// This is the ONLY place detector logic lives. Everything else - the ladder,
// the UI, the scoring, the draw pools - must work unchanged when this is swapped.
export async function runDetector(
  image: Buffer,
  level: 1 | 2 | 3
): Promise<DetectorVerdict> { ... }
```

`DetectorVerdict` must be shaped like a real multi-signal detector response, because that is what the UI renders and what the real API will return:

```ts
interface DetectorVerdict {
  fooled: boolean;              // true = the visitor beat this level
  confidence: number;           // 0-1
  signals: {                    // per-signal breakdown, rendered as a list
    name: string;               // e.g. 'Frequency-domain artefacts'
    verdict: 'synthetic' | 'authentic' | 'inconclusive';
    score: number;              // 0-1
  }[];
  heatmapRegions: {             // normalised 0-1 boxes over suspect areas
    x: number; y: number; w: number; h: number; intensity: number;
  }[];
  latencyMs: number;
}
```

For the stub: derive a deterministic pseudo-random result from a hash of the image bytes so the same image always gets the same verdict (visitors will retry and notice inconsistency). Weight it so level 1 is beatable roughly 35% of the time, level 2 about 15%, level 3 about 4%. Generate 2-4 plausible heatmap boxes weighted toward the image centre and upper third where faces sit. Add a realistic 900-1800ms latency so the "detectors running" animation has something to cover.

Name at least five signals so the panel looks like a real product: frequency-domain artefacts, noise-residual consistency, facial-landmark geometry, compression-history analysis, colour-channel correlation.

## The reveal - the most important screen in this game

Show the uploaded image with the **heatmap overlaid** as translucent warm boxes, and the signal breakdown ticking in one row at a time with a short stagger. Do not resolve all five at once; the suspense is the product demo.

Then the verdict, large and unambiguous: **DETECTED** or **FOOLED US**. On a detection, name the single strongest signal in plain language - "the noise residual across your image is too uniform to be camera output." On a fool, be a good sport about it and immediately raise the stakes for the next level.

## Uploads

Accept JPEG, PNG and WebP up to 10 MB. Reject anything else with a clear message. Store uploads in Replit's object storage or the filesystem under `/tmp` keyed by run id, and **write a scheduled purge that deletes every upload older than 24 hours** - this is a DPDP commitment in the event plan, not a nice-to-have. Add a visible "images are deleted within 24 hours" note on the upload screen.

Add a basic content gate: reject images whose filename or EXIF description contains obvious slurs, and give the host panel a one-tap "remove this upload" control. A trade-show floor needs an escape hatch.

## Run detail to store

```json
{ "attempts": [ {"level":1,"fooled":true,"confidence":0.42},
                {"level":2,"fooled":false,"confidence":0.88} ],
  "laddderReached": 2, "quitVoluntarily": false,
  "drawPool": null, "tier": "Achiever" }
```

Store `drawPool` as `'airpods'` for players who fooled exactly 2, `'ipad'` for all 3, otherwise null. The host needs to pull those two pools at the Day 2 finale, so expose them in the admin panel as exportable lists.

# GAME 3 - Fraud Detective

Five graph investigation cases plus a bonus trivia round. Caps at **100 points**.

Read `CASES`, `PRIMER` and `BONUS` from the Fraud Detective data block.

## Flow

Rules screen, then the **primer** (`PRIMER` - a short explainer on community detection with a small two-cluster diagram showing a bridge account), then five cases in order, then the bonus round, then the summary.

## Each case

Two-pane layout. On a kiosk that is a left case-file panel and a right graph canvas; on a phone the graph goes on top and the case file scrolls underneath.

**Left panel - the case file:**
- Sector tag (`sector`) and case title
- "CASE NOTES" header with the line "unfiled - nobody's connected these yet" in a mono, slightly hand-filed style
- The three `clues`, each as a note card on a vertical thread with a small amber pin
- The `brief` paragraph, then the `instruction` in italics
- A "WRONG GUESSES: n" counter
- **Submit Accusation** (disabled until a node is selected) and **Reveal Answer** buttons

**Right panel - the graph:**
- Force-directed node-link layout from `nodes` and `edges`. Nodes are labelled circles; tapping one selects it and rings it in Bureau blue.
- Colour nodes by `clusters` so the communities read at a glance, but **do not visually mark the answer** - finding it is the game.
- Render `edgeLabels` on the relevant edges and `nodeLabels` beside nodes (amounts, "guarantees").
- Must be **pan and pinch-zoom** on touch, with a reset-view button. Fix the layout seed per case so it looks identical on every play and the host can learn it.
- On a correct submission, animate the answer node to green and highlight its edges.

## Case scoring - 16 points per case, 80 across five

| Result | Points |
|---|---|
| Correct, no wrong guesses | 16 |
| Correct after 1 wrong guess | 10 |
| Correct after 2 wrong guesses | 6 |
| Correct after 3+ wrong guesses | 2 |
| Revealed without solving | 0 |

There is no timer and no game over. Every case is attemptable and the player always reaches the bonus round, because the explanations are the sales content and cutting people off before they read them defeats the purpose.

After each case, show the `explanation` and the `hook`, with a Next Case button.

## Bonus round - Six Degrees, 20 points

Four questions, 5 points each, from `BONUS`. This is deliberately **not** fraud - it is Kevin Bacon film trivia, and the tonal break is the point.

Render concentric dashed rings labelled 1, 2 and 3 degrees with Kevin Bacon at the centre. For each of the four figures, the player taps the ring they think that person sits on. 5 points for a correct ring, 0 otherwise, no penalty. After each answer, animate the figure snapping onto its true ring with a connecting path.

Close on the `payoff` text, which lands the actual argument: almost nobody is more than three hops from anyone else, so "these two accounts have no connection" is nearly always false. The interesting question is not whether a path exists but how short and how deliberate it is. That is the bridge back to fraud graphs, and it is the line the host should be ready to pick up.

**Flag for the team, not for the build:** the four degree values in the data are marked `caution` and need verifying against oracleofbacon.org before the event. Surface that caution string in the admin panel so nobody forgets.

|---|---|---|

## Leaderboard screens

**Live board** - full-screen, designed to be readable across the booth on a wall display. Rank, first name, company, the three per-game scores as small badges, bonus badge, total. Top 10 plus the current player's row pinned at the bottom if they are below the cut. Poll every 10 seconds; animate rank changes so movement catches the eye.

**Today vs cumulative** - a toggle. Today's board resets daily; the cumulative board spans the event and decides the Event Champion at the Day 2 5 PM finale.

**Per-game boards** - three tabs so someone who only played one game still sees themselves ranked.

Seed 12 plausible fake entries (Indian first names, real-sounding Indian fintech and bank company names, scores spread 25-280) so the board never looks empty on day one morning. Mark them `is_demo` in the database and give the admin panel a one-tap "clear demo rows" button for the moment real traffic starts.

# Host / admin panel at /admin

Gate it behind a simple passcode from an env var - not real auth, just enough that a curious visitor cannot reach it. It needs:

- Live counts: plays per game, unique players, plays by kiosk vs phone
- Lead export as CSV: name, email, phone, company, consent timestamp, games played, tier per game, total points
- The two Spoof draw pools (AirPods qualifiers, iPad qualifiers) as exportable lists
- Per-question accuracy for Spot the Fraud and per-case accuracy for Fraud Detective, so a broken or impossible item can be spotted and pulled mid-event
- A read-only answer-and-rationale view per question, for settling disputes at the station
- Grant a goodwill re-run to a named player
- Remove a Spoof upload
- Clear demo leaderboard rows
- The Six Degrees verification caution, displayed prominently until someone ticks it off

# Design

Dark, confident, fintech-serious. This sits beside enterprise sales conversations, so no cartoon gamification.

- Background `#0B1220`, surfaces `#151E33`, panels `#1B2A4A`
- Bureau blue `#2E5BFF` for primary actions and focus rings
- Correct `#0FA968`, wrong `#E5484D`, near-miss and case-note pins amber `#F5A623`
- Sans-serif throughout with tight heading tracking. A mono face for account IDs, case notes and code-like labels - it makes the investigation screens feel like a real tool.
- **Kiosk target is 1080x1920 portrait touch.** Question text at least 22px, options at least 18px, every tap target at least 64px tall. No hover-only affordances anywhere.
- **Phone must work properly**, not just technically render - it is a first-class path via QR, and for Spoof it is the main path.
- Motion 200-300ms with a spring on selection. Never add waiting time to a queue.
- Accessibility: never signal correctness by colour alone, always pair with an icon and text. Keyboard navigable. Respect `prefers-reduced-motion`.

**Attract loop** on each kiosk when idle for 45 seconds: game name, a rotating fraud stat, the top 5, and a large QR. It has to pull someone in from three metres away.

# Reliability - this runs on venue WiFi

- Every write goes through an API route that returns fast and is safe to retry. Use an idempotency key per run so a double-tap on a flaky connection cannot double-post a score.
- Wrap the run-submission write in a **transaction** and do the best-run comparison inside it. Two kiosks finishing a run for the same email in the same second must not race. This is the specific thing the key-value store could not have given us.
- If the database is unreachable, queue the run in memory, show "score will sync" rather than an error, and retry with backoff. Never lose a play and never block a player on a network round trip.
- Graph rendering, question flow and the detector stub must all work with no network after initial load.
- A kiosk reload must never lose the current run - persist run progress server-side on each level transition, keyed by run id in the URL.

# Database notes worth getting right

- Replit's Postgres is **serverless (Neon-backed)**, so it sleeps and it counts connections. Use a single shared Drizzle client as a module-level singleton, not a new client per request - Next.js route handlers will otherwise exhaust the connection pool under kiosk polling. In dev, cache the client on `globalThis` so hot reload does not leak connections on every save.
- The leaderboard polls every ten seconds from up to four screens at once. Serve it from a **single query against a view**, not from several round trips stitched together in JavaScript.
- Store `event_day` as a real date column derived in **Asia/Kolkata**, not UTC. A run at 11:30 PM IST on day one belongs to day one; computing the day from a UTC timestamp puts it on day two and quietly corrupts the daily leaderboard and the 5 PM draw.
- Index `runs(player_id, game)` and `runs(event_day, game)`. Without them the leaderboard view degrades as the event fills up, and it will be at its slowest exactly when the booth is busiest.
- Never store aggregate or total scores. Every total is derived. A stored total is a total that will drift from its runs.

# Acceptance tests - run these before calling it done

1. Spot the Fraud level points sum to exactly 100, and a clean ten-level run scores 100.
2. **Option order is shuffled on display, and a correct answer still scores as correct at every one of the ten levels.** The authored `correct` arrays are 1-based indices into the original option order, so map through the shuffle rather than mutating the key. This is the single most likely bug in the whole build - test it explicitly at Levels 6, 8 and 10 where multiple answers are correct.

10. Entry form rejects a 9-digit phone, a malformed email and an unticked consent box.
